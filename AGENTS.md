# Инструкции для AI-агентов: лига Mr. Pushkin

Этот файл — точка входа. Прочитайте его целиком перед первым изменением. Он короткий
намеренно: детали лежат в `docs/`, и на них есть ссылки.

Проект сделан одним разработчиком при поддержке AI-агентов. Ценятся аккуратные,
минимальные и проверенные изменения, а не объём переписанного кода.

---

## 1. Что это за проект

Сайт любительской теннисной лиги клуба **Mr. Pushkin** в Пушкине (Санкт-Петербург):
турниры, рейтинг, игроки, новости, архив, кабинет игрока и кабинет организатора.

- Продукт продаётся клубу целиком: код, база и файлы принадлежат разработчику,
  клуб получает право пользования и выгрузку данных.
- Один клуб в MVP. Мультиклубность — возможное расширение, не текущая задача.
- Онлайн-оплаты нет: взносы фиксируются в заявке, деньги принимаются вне системы.
- Вся продуктовая конкретика — `docs/PRODUCT.md`.

## 2. Текущее состояние

Это **UI-прототип**, а не готовый бэкенд:

- данные — `src/lib/mock`, доступ — через `src/lib/data`;
- БД, серверной авторизации и загрузки файлов нет;
- регистрация и подтверждение аккаунтов — через Go API (`src/lib/api/auth.ts`, см. `docs/LOCAL_API.md`);
- действия организатора не сохраняются;
- сборка уже умеет `output: "standalone"` и секретный `basePath`.

Не выдавайте прототип за продакшн. Если задача требует постоянного хранения, сначала
проверьте, не описан ли бэкенд в плане и не пора ли его делать.

## 3. Стек и команды

- Next.js 16 (App Router), React 19, TypeScript, Tailwind 4.
- Иконки — только `lucide-react`.
- Шрифты — Prata (заголовки) и Manrope (текст) через `next/font/google`.
- Целевая архитектура (D-017): **UI — Next.js**, **API — Go**, **БД — PostgreSQL 17**
  (pgx + sqlc + goose). Авторизация только на Go: Argon2id (проверка по хэшу, не `==`),
  серверные сессии, AES-256-GCM для секретов в БД. Один клуб (D-018).

```bash
npm install
npm run dev        # http://localhost:3000
npm run typecheck  # обязательно перед завершением задачи
npm run build      # обязательно, если меняли маршруты, конфиг или UI-серверный код
```

Node.js 22, см. `.nvmrc`. Go API (когда появится): `server/`, тесты `go test ./...`.

## 4. Карта репозитория

```text
src/app/(public)/     публичные страницы
src/app/(auth)/       вход и регистрация
src/app/organizer/    кабинет организатора
src/app/cabinet/      кабинет игрока
src/components/       ui, domain, organizer, layout
src/lib/data/         слой доступа UI (сейчас mock; позже HTTP к Go)
src/lib/mock/         демо-данные
src/lib/domain.ts     категории, типы, статусы, клубные константы
src/lib/types.ts      доменные типы
src/lib/api/auth.ts   HTTP-клиент auth и заявок организатора
server/               Go API (целевое; этап 2+)
deploy/               nginx и деплой на Pi
docs/                 продукт, архитектура, дизайн, рейтинг, решения
```

Правило: страницы не импортируют `src/lib/mock` напрямую и не ходят в Postgres.
Данные UI — через `src/lib/data` или `/api` Go. Бизнес-правила и пароли — только в Go.

## 5. Жёсткие продуктовые правила

1. **Только взрослый теннис.** В продукте нет детей, юниоров, детских турниров, лагерей,
   школ для детей и детских зачётов. Не добавляйте такие категории, тексты, изображения
   и поля. Если задача выглядит как «вернуть детский турнир», уточните у владельца.
2. **Весь интерфейс на русском.** Английский — только в коде, именах переменных и
   технических терминах. Никаких «coming soon» и английских заглушек в UI.
3. **Один клуб.** Не добавляйте `club_id`, выбор клуба и мультитенантность без решения.
4. **Онлайн-оплаты нет.** Не подключайте ЮKassa, Stripe и подобные сервисы.
5. **Регистрация:** любой создаёт аккаунт → статус «на проверке» → организатор
   подтверждает имя, фамилию и уровень → только после этого вход. Не упрощайте поток
   до «зарегистрировался и сразу вошёл».
6. **Роли:** `player < organizer < owner < superadmin`. В прототипе реальных проверок
   ролей нет; в продакшене любая проверка прав — на сервере, UI не является защитой.
7. **Фотографии** временно взяты с сайта клуба. Не добавляйте новые фото из интернета
   и не удаляйте существующие без согласования.

## 6. Дизайн: EDITORIAL

Полная система — `docs/DESIGN.md`. Коротко:

- бумага `#eaece5`, чернила `#23250f`, один акцент — глянцевый мяч;
- Prata для крупных заголовков, Manrope для текста, микропрописные подписи;
- волосяные линии вместо теней и рамок, скругления только у кнопок и аватаров;
- никаких градиентов, стекла, неона и «SaaS-карточек»;
- сетка держит воздух, заголовки крупные, тексты короткие;
- иконки только Lucide, один стиль штриха;
- проверяйте 1440 px и 390 px, горизонтального скролла быть не должно.

Не «улучшайте» дизайн произвольно: сначала прочитайте `docs/DESIGN.md` и посмотрите
соседние страницы.

## 7. Работа с продакшн-кодом

Полные правила — `docs/PRODUCTION-RULES.md`. Обязательный минимум:

- **Не комментируйте правки пользователя.** Запрещены фразы вроде «о, я тут сделал,
  как вы просили))», «как и просили», «готово!», эмоциональные вставки в код, доки и
  ответы. Просто сделайте работу и опишите результат нейтрально.
- **Никаких эмодзи** в коде, документации, коммитах и интерфейсе.
- **Минимальный диф.** Не переформатируйте файлы целиком, не переименовывайте без
  необходимости, не удаляйте чужой код «по пути».
- **Не перезаписывайте правки пользователя.** Если файл изменён не вами — прочитайте
  его и сохраните намерение автора.
- **Комментарии только там, где неочевидна причина.** Не комментируйте очевидное.
- **Никаких секретов в коде, логах и git.** Пароли, токены и `.env.deploy` не коммитятся
  и не печатаются в ответах.
- **Не добавляйте зависимости** без явной необходимости и объяснения.
- **Не делайте деструктивных операций** (удаление данных, `git reset --hard`, перезапись
  ветки, деплой) без подтверждения, если задача прямо этого не требует.

## 8. Проверка перед завершением

Перед словами «готово»:

1. `npm run typecheck` — без ошибок.
2. `npm run build` — если менялись маршруты, `next.config.ts`, серверные компоненты
   или стили, влияющие на сборку.
3. Для UI — открыть затронутые страницы на 1440 и 390 px, проверить консоль и ссылки.
4. Для регистрации/подтверждения — пройти поток: регистрация → статус «на проверке» →
   подтверждение организатором → вход.
5. Убедиться, что в диффе нет `.env.deploy`, `node_modules`, `.next`, `*.tsbuildinfo`.

Не заявляйте об успехе без вывода проверки. Если проверка не запускалась — так и скажите.

## 10. Деплой

Текущая площадка: Raspberry Pi 5, `dima@91.223.89.199`, домен
`mrpushkin.duckdns.org`. Приложение в Docker на `127.0.0.1:3010`, внешний nginx
проксирует секретный префикс и требует Basic Auth.

```bash
./deploy/deploy-pi.sh
```

Скрипт читает `.env.deploy` (не в git). Полный runbook, проверки и ограничения —
`docs/DEPLOY.md`. Не публикуйте пароли и секретный путь в ответах и коммитах.
Перед деплоем убедитесь, что сборка и typecheck проходят.
