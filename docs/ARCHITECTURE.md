# Архитектура лиги Mr. Pushkin

**Статус:** черновик к согласованию, ревизия 2 от 18.11.2026.
**Область:** публичный сайт, кабинет игрока, кабинет организатора, супер-админка, API, база данных, деплой и эксплуатация.

> **Текущее состояние (ноябрь 2026).** В репозитории работает UI-прототип без базы данных и серверной
> авторизации: данные берутся из `src/lib/mock`, регистрация и подтверждение аккаунтов хранятся
> в localStorage браузера. Документ описывает целевое продакшн-состояние. Реальный деплой уже
> устроен иначе, чем в первых ревизиях: Docker + внешний nginx на Pi, без Caddy; подробности —
> в `docs/DEPLOY.md` и решении D-013. Лига ведёт только взрослые турниры: детских и юношеских
> категорий в продукте нет.

## 1. Контекст и цели

Клуб продаёт лигу как готовый продукт с ежемесячным техническим сопровождением. Код, база и файлы принадлежат разработчику; клуб получает право пользования и выгрузку своих данных. Поэтому архитектура не должна зависеть от внешнего BaaS и должна переноситься с домашней Raspberry Pi 5 на серверы Selectel без переписывания приложения.

Цели:

1. **Свой бэкенд.** Приложение, база, авторизация, файлы и фоновые задачи работают на нашей инфраструктуре.
2. **Безопасность по умолчанию.** Минимальная поверхность атаки, явные проверки прав на сервере, аудит, шифрованные бэкапы.
3. **Работа на Raspberry Pi 5 / 8 ГБ.** Один сервер, Docker Compose, без тяжёлых платформ.
4. **Простой переезд.** Перенос на Selectel — это restore дампа, запуск того же compose и переключение DNS.
5. **Один разработчик.** Минимум компонентов, понятные runbook-и, автоматизация миграций и бэкапов.

## 2. Ключевые решения

| № | Решение | Альтернатива | Почему так |
|---|---|---|---|
| 1 | Собственный backend на Next.js (server actions + route handlers) | Supabase, Firebase, отдельный NestJS | Один деплой, полный контроль, нет внешнего BaaS и его лимитов; для одного разработчика меньше движущихся частей |
| 2 | PostgreSQL 17 в Docker | SQLite, MySQL | Транзакции, ограничения, оконные функции для рейтинга, зрелые бэкапы; SQLite плохо подходит для конкурентных заявок |
| 3 | Drizzle ORM + SQL-миграции | Prisma | Лёгкий рантайм, явный SQL, миграции ревьюятся глазами, хорошо работает на arm64 |
| 4 | Своя авторизация: Argon2id + серверные сессии | Auth.js, Supabase Auth | Полный контроль над сессиями, блокировками и аудитом; нет зависимости от чужого жизненного цикла |
| 5 | Сессии в Postgres, токен в HttpOnly-cookie | JWT в localStorage | Токен нельзя украсть через XSS, сессию можно отозвать мгновенно |
| 6 | Роли: player → organizer → owner → superadmin | Только admin | Владелец клуба и разработчик — разные роли; superadmin нужен для сопровождения |
| 7 | Файлы на локальном диске + offsite-бэкап | S3 сразу | На Pi дешевле и быстрее; интерфейс storage абстрагирован, позже переезд на S3 Selectel |
| 8 | nginx + certbot на хосте Pi, приложение в Docker | Caddy внутри контейнера | На Pi 80/443 уже заняты другими проектами; nginx остаётся TLS-терминатором и пускает приложение только по секретному пути на время разработки |
| 9 | Один клуб в MVP | Мультитенантность | Не усложняем схему; брендинг и настройки уже вынесены в `settings`, миграция на `club_id` возможна позже |
| 10 | Онлайн-оплата не входит | ЮKassa | Взносы фиксируются в заявке, оплата вне системы |

## 3. Схема системы

```text
Интернет
   │
   ├── 80/443 → nginx (host)
   │              ├── /.well-known/acme-challenge/ → certbot webroot
   │              ├── /images/*                    → /var/www/mrpushkin/images
   │              ├── /<secret-path>/*             → Next.js 127.0.0.1:3010
   │              └── всё остальное                → 404
   │                 (на время разработки — Basic Auth)
   │
   ├── SSH 22 (только ключи, UFW, fail2ban)
   │
Docker network (внутренняя)
   ├── web        Next.js standalone, Node 22, non-root
   ├── db         PostgreSQL 17, порт наружу не публикуется
   ├── migrate    одноразовый контейнер миграций
   ├── backup     cron: pg_dump + uploads → шифрование → rclone
   └── duckdns    обновление A-записи
```

Внешние сервисы: SMTP-провайдер для писем, Sentry для ошибок, внешний uptime-монитор, S3-совместимое хранилище для бэкапов (Selectel/B2). Все секреты — в `.env` на сервере, не в образе и не в git.

| Слой | Технология | Комментарий |

| UI | Next.js 16 App Router, React 19, Tailwind 4, Lucide | Прототип уже на этом стеке; иконки — только Lucide |

| БД | PostgreSQL 17 | `citext`, `pgcrypto`, `pg_trgm` для поиска |
| ORM | Drizzle ORM + `pg` | Пул 10 соединений |
| Auth | `@node-rs/argon2`, `otpauth`, Node `crypto` | Argon2id, TOTP |
| Файлы | `sharp` | Ресайз, WebP, strip EXIF |
| Почта | Nodemailer + SMTP клуба/Unisender | Очередь в БД, повторные попытки |
| Тесты | Vitest, Playwright | Unit + e2e |
| CI | GitHub Actions | lint, typecheck, test, build, audit |
| Деплой | Docker Compose, nginx (host), certbot, DuckDNS | Pi 5 сейчас, Selectel позже |

**Почему не Supabase.** Self-hosted Supabase на Pi — это 7–9 контейнеров, 2–3 ГБ RAM в простое, Studio и Kong как дополнительная поверхность атаки, отдельный цикл обновлений и свои лимиты. Для одного клуба и одного разработчика собственный слой на Next.js + Postgres проще, безопаснее и легче переносится. Supabase-пакеты из проекта удаляются на этапе 1.

## 6. Аутентификация

### 6.1 Пароли

- Argon2id: memory 19 MiB, iterations 2, parallelism 1; параметры хранятся в строке хэша, чтобы их можно было поднять без сброса паролей.
- Минимум 10 символов, проверка по списку популярных паролей, запрет email в пароле.
- Хэш никогда не логируется и не отдаётся в API.
- Смена пароля отзывает все сессии, кроме текущей.

### 6.2 Сессии

- 32 случайных байта, в cookie — только токен, в БД — SHA-256 от него.
- Cookie: `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, без `Domain`; в production имя `__Host-mpl_session`.
- Абсолютный срок 30 дней, простой 7 дней; продление при активности не чаще раза в час.
- Отзыв: выход, смена пароля, блокировка пользователя, подозрительный вход.
- В БД: IP, user-agent, последняя активность. Пользователь видит список сессий и может завершить любую.

### 6.3 Регистрация и сброс

**Регистрация с подтверждением администратором.** Любой может создать аккаунт: имя, фамилия, email, пароль и предварительный уровень. Аккаунт получает статус `pending` и не может войти. Организатор в разделе «Заявки игроков» проверяет и при необходимости исправляет имя, фамилию и уровень, затем подтверждает или отклоняет заявку. Только после статуса `approved` авторизация считается пройденной. Решение фиксируется в аудите, игрок получает письмо; отклонённый аккаунт видит статус при попытке входа.

- Email подтверждается одноразовой ссылкой (32 байта, 24 часа, хранится хэш).
- Сброс пароля: 30 минут, одноразовый, все сессии отзываются после смены.
- Ответы не раскрывают, существует ли аккаунт.
- Заявка на турнир требует подтверждённого email.

### 6.4 Двухфакторная аутентификация

- TOTP для `owner` и `superadmin` обязателен; для организатора — по желанию.
- Секрет хранится зашифрованным ключом из env (`APP_ENCRYPTION_KEY`), не в открытом виде.
- 8 резервных кодов, хранятся хэшами, одноразовые.
- Включение 2FA — через подтверждение пароля и проверку кода.

### 6.5 Защита входа

- Лимит: 5 неудачных попыток за 15 минут на пару «IP + аккаунт», затем экспоненциальная задержка до 15 минут.
- Глобальный лимит на IP: 30 попыток в час.
- Уведомление владельцу о входе superadmin и о серии неудачных попыток.
- Время ответа выравнивается, чтобы не давать оракул по существованию email.

## 7. Роли и права

Иерархия: `player < organizer < owner < superadmin`. Роль хранится в `users.role`, проверяется на сервере при каждом действии. UI — только подсказка, не защита.

| Действие | player | organizer | owner | superadmin |
|---|:---:|:---:|:---:|:---:|
| Публичные страницы | ✓ | ✓ | ✓ | ✓ |
| Свой профиль, заявки, матчи | ✓ | ✓ | ✓ | ✓ |
| Чужие персональные данные | — | ✓ | ✓ | ✓ (в журнале) |
| Турниры, заявки, сетки, матчи | — | ✓ | ✓ | ✓ |
| Игроки: спортивные данные | — | ✓ | ✓ | ✓ |
| Новости и события | — | ✓ | ✓ | ✓ |
| Рейтинг: пересчёт | — | ✓ | ✓ | ✓ |
| Рейтинг: ручная корректировка | — | — | ✓ | ✓ |
| Роли организаторов | — | — | ✓ | ✓ |
| Настройки клуба, брендинг | — | — | ✓ | ✓ |
| Журнал аудита | — | — | ✓ | ✓ |
| Роль owner | — | — | — | ✓ |
| Системные настройки, интеграции | — | — | — | ✓ |
| Бэкапы, миграции, feature flags | — | — | — | ✓ |
| Удаление аудита | — | — | — | — |

**Superadmin — это разработчик.** Его права шире владельца только в системном контуре: управление владельцами, интеграциями, бэкапами, миграциями и флагами. Он не может удалять аудит, незаметно менять результаты или читать пароли. Все его действия пишутся в журнал, владелец получает еженедельную сводку. Прямое изменение пароля владельца запрещено — только ссылка на сброс и разблокировка.

**Защита от локаута:** нельзя снять роль с последнего owner/superadmin; нельзя удалить самого себя; superadmin создаётся только CLI-командой на сервере, не через публичную регистрацию.

**Имперсонация** (просмотр глазами игрока) — только read-only, с баннером и записью в аудите; любые действия отключены.

## 8. Безопасность

### 8.1 Модель

- **Deny by default.** Каждый server action начинается с `requireUser()` и `requireRole()`/`can()`. Нет «страницы только для админа» без серверной проверки.
- **Политики в одном месте.** `server/auth/rbac.ts` описывает действия, а не разбросанные `if (role === ...)`.
- **Тесты прав.** Матрица «роль × действие» проверяется unit-тестами и e2e.
- **Аудит.** `audit_log` заполняется сервисным слоем: кто, что, до/после, IP, user-agent. Триггер запрещает UPDATE/DELETE.

### 8.2 Входные данные

- Zod-схемы для каждой формы и каждого action, ограничения длины и допустимых значений.
- Параметризованные запросы через Drizzle; никакой конкатенации SQL.
- Загрузка файлов: проверка magic bytes, декодирование `sharp`, лимит 8 МБ, запрет SVG.
- HTML из редактора новостей санитизируется на сервере (allowlist тегов).

### 8.3 Веб-защита

- CSP с nonce, `default-src 'self'`, `object-src 'none'`, `frame-ancestors 'none'`.
- HSTS 1 год, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` без камеры/микрофона.
- CSRF: `SameSite=Lax` + проверка `Origin` для действий, меняющих состояние.
- Rate limit на вход, регистрацию, сброс, контактную форму, загрузку.
- Ограничение размера тела запроса на уровне Caddy.

### 8.4 Инфраструктура

- UFW: только 22, 80, 443; PostgreSQL наружу не смотрит.
- SSH: только ключи, root-логин запрещён, fail2ban, нестандартный порт не обязателен.
- Автоматические обновления безопасности ОС; ручное обновление контейнеров после бэкапа.
- Контейнеры работают не от root, `read_only` где возможно, без `--privileged`.
- Секреты: `.env` с правами 600, владелец — deploy-пользователь; ротация при подозрении.
- Разделение ролей БД: `app` (DML), `migrator` (DDL), `backup` (чтение дампа). Пароли разные.

### 8.5 Мониторинг безопасности

- Алерты: серия неудачных входов, вход superadmin, ошибка бэкапа, заполнение диска > 80%, 5xx > 1%.
- Sentry без персональных данных в breadcrumbs.
- Ежемесячный просмотр аудита и `npm audit`; обновления зависимостей — раз в две недели.

### 8.6 Приватность (152-ФЗ)

- Минимизация: публично — имя, город, категория, рейтинг, фото; телефон, email, дата рождения — только организатору.
- Согласие на обработку ПД и публикацию фото — отдельные чекбоксы, журнал согласий.
- Экспорт и удаление аккаунта по запросу; удаление — soft delete с обезличиванием через 30 дней.
- Данные и бэкапы — в РФ (Pi у клуба/в офисе, S3 Selectel).

## 9. Данные и целостность

- **Транзакции.** Заявка, подтверждение, генерация сетки, ввод счёта, пересчёт рейтинга — в одной транзакции с блокировкой строк.
- **Ограничения в БД.** Уникальность заявки `(tournament_id, player_id)`, вместимость проверяется функцией под `SELECT ... FOR UPDATE`, а не только в приложении.
- **Мягкое удаление.** `deleted_at` у игроков, турниров, новостей; физическое удаление — только скриптом с бэкапом.
- **Аудит.** Append-only, хранит diff в `jsonb`.
- **Идемпотентность.** Уникальные ключи для webhook/повторных операций, повторный ввод счёта не дублирует события.
- **Время.** В БД — `timestamptz` UTC, отображение — Europe/Moscow.

---

## 10. Файлы и изображения

- Загрузка в `/data/uploads/{bucket}/{yyyy}/{mm}/{uuid}`.
- `sharp` создаёт 320/640/1280 px в WebP, удаляет EXIF, считает blurhash.
- Публичные изображения отдаёт Caddy с `Cache-Control: public, max-age=31536000, immutable`; имя содержит хэш.
- Приватные документы — через route handler с проверкой прав и `Content-Disposition: attachment`.
- Метаданные в таблице `files`: mime, размер, ширина/высота, checksum, автор.
- Лимит 8 МБ на файл, квота на клуб — 2 ГБ (на Pi), позже S3.
- Бэкап uploads входит в ежедневный архив.

## 11. Почта

- SMTP-провайдер с доменом клуба: SPF, DKIM, DMARC.
- Очередь `email_outbox`: статус, попытки, `next_attempt_at`, ошибка.
- Шаблоны: подтверждение email, сброс пароля, заявка подтверждена/отклонена/лист ожидания, напоминание о матче, результат турнира.
- Повторные попытки с backoff, максимум 5; после — алерт.
- Отписка от дайджеста, но не от транзакционных писем.
- На Pi исходящий 25-й порт часто закрыт — используем API/SMTP 465 провайдера.

## 12. Деплой на Raspberry Pi 5

### 12.1 Подготовка

1. Raspberry Pi OS Lite 64-bit, загрузка с NVMe/USB SSD (не с SD-карты).
2. Статический IP в локальной сети, проброс 80/443 на роутере; проверить, что провайдер не использует CGNAT.
3. Docker Engine + Compose plugin, пользователь `deploy` в группе `docker`.
4. UFW, fail2ban, unattended-upgrades, SSH только по ключам.
5. DuckDNS-домен `mrpushkin.duckdns.org`, токен в env.
6. `docker compose up -d`, миграции, создание superadmin, проверка `/api/health`.

### 12.2 Compose

- `web`: Next standalone, `NODE_ENV=production`, `mem_limit: 1536m`, healthcheck.
- `db`: `postgres:17-alpine`, volume `pgdata`, `shared_buffers=1GB`, `effective_cache_size=3GB`, `work_mem=16MB`, `max_connections=40`.
- `migrate`: тот же образ, команда `node scripts/migrate.js`, запускается до web.
- `nginx` (host, не контейнер): 80/443, сертификаты certbot, статика `/images`, проксирование приложения по секретному префиксу; конфиги — в `deploy/nginx/`.
- `backup`: cron-контейнер, `pg_dump`, tar uploads, `age`, `rclone`.
- `duckdns`: обновление IP раз в 5 минут.

### 12.3 TLS и CGNAT

- nginx на хосте получает сертификат Let's Encrypt через `certbot --webroot` для DuckDNS-домена; продление — `certbot.timer`, проверка `certbot renew --dry-run`.
- Пока продукт не готов, домен закрыт Basic Auth и секретным префиксом пути `NEXT_BASE_PATH`; корень и остальные пути отдают 404. Это временная защита, не замена ролям и 2FA.
- Если провайдер не даёт белый IP (CGNAT), проброс портов невозможен. Варианты: собственный домен, делегированный в Cloudflare, и Cloudflare Tunnel; либо временно Tailscale Funnel/ngrok. Приложение при этом не меняется, меняется только входной контур.

### 12.4 Производительность

- Next standalone, без dev-зависимостей в образе.
- Публичные страницы кэшируются ISR, инвалидация по тегам.
- Изображения пре-генерируются при загрузке, чтобы не нагружать CPU Pi.
- Пул БД 10 соединений, таймауты 5 с.
- Сборка: лучше в GitHub Actions под `linux/arm64` и push в GHCR; сборка на Pi — с `--max-old-space-size=2048` и swap 2 ГБ.
- Ожидаемая нагрузка: 50–200 посетителей в день, пик — день турнира; конфигурации хватает с запасом.

## 13. Бэкапы и восстановление

- Ежедневно 03:15: `pg_dump -Fc`, tar uploads, шифрование `age`, выгрузка в S3 (Selectel/B2) и на внешний диск.
- Хранение: 14 ежедневных, 8 недельных, 6 месячных.
- Перед каждой миграцией — внеочередной дамп.
- Раз в месяц — учебное восстановление на staging с проверкой контрольных запросов.
- RPO — 24 часа, RTO — 2 часа.
- Runbook `deploy/restore.md`: поднять пустую БД, restore, проверить пользователей, турниры, файлы, переключить трафик.

## 14. Мониторинг и эксплуатация

- `/api/health`: версия, доступность БД, свободное место, время ответа; без секретов.
- UptimeRobot раз в 5 минут, алерт в Telegram и на почту.
- Sentry: клиент, сервер, edge; фильтрация ПД.
- Логи Docker с ротацией 10 МБ × 3; ошибки дублируются в Sentry.
- Еженедельно: просмотр ошибок, места на диске, бэкапов, обновлений безопасности.
- Обновление приложения: бэкап → миграции → деплой → smoke-тест; откат — предыдущий образ.
- Инциденты: изоляция пользователя, смена паролей/ключей, восстановление из бэкапа, публикация статуса на сайте.

## 15. Переезд на Selectel

1. Создать VPS/облачную БД в РФ, тот же compose, версии зафиксированы.
2. Развернуть пустую схему, восстановить последний дамп и uploads.
3. Прогнать smoke- и e2e-тесты на новом контуре.
4. Переключить DNS (снизить TTL за сутки), проверить TLS.
5. Оставить Pi как холодный резерв на 2 недели, затем выключить.
6. Обновить runbook и доступы.

Никаких изменений в коде: только env, DNS и, при желании, managed PostgreSQL вместо контейнера.

## 16. Тестирование

- **Unit (Vitest):** формула рейтинга, генератор сеток, RBAC, пароли/токены, парсеры.
- **Integration:** сервисы на тестовой БД, транзакции, лимит участников, лист ожидания, перенос победителя.
- **E2E (Playwright):** регистрация → заявка → подтверждение → сетка → счёт → рейтинг; вход/выход; права ролей.
- **Security:** матрица доступа, попытки CSRF, загрузка вредоносного файла, rate limit.
- **Нагрузка:** 200 одновременных читателей главной и рейтинга (k6), пиковый ввод счетов.
- CI блокирует merge при падении typecheck, lint, unit, e2e, `npm audit high`.
