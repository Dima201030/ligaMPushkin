## D-001. Собственный бэкенд вместо Supabase

**Дата:** 16.11.2026.
**Контекст:** продукт продаётся клубу с ежемесячным сопровождением; нужен контроль над данными, доступом и стоимостью.
**Варианты:** Supabase Cloud, self-hosted Supabase, собственный backend на Next.js + PostgreSQL.
**Решение (исходное):** собственный backend. Next.js server actions + PostgreSQL + Drizzle, своя авторизация.
**Статус:** заменено решением **D-017** (18.11.2026): API на Go, UI на Next.js.
**Следствия исходного:** убираем `@supabase/*`; полный контроль; один compose на Pi.
**Связано:** `ARCHITECTURE.md`, D-017.

## D-002. База и доступ к данным

**Дата:** 16.11.2026; обновлено 18.11.2026.
**Контекст:** нужны транзакции, ограничения и оконные функции для рейтинга.
**Варианты:** SQLite, MySQL, PostgreSQL; Prisma, Drizzle, sqlc + goose.
**Решение:** PostgreSQL 17. Доступ из Go: `pgx` + `sqlc` (типизированные запросы) + `goose` (SQL-миграции).
**Следствия:** SQL ревьюится глазами; рантайм лёгкий; arm64 поддерживается. Prisma и Drizzle для API не используются.
**Связано:** D-017.

## D-003. Авторизация

**Дата:** 16.11.2026; обновлено 18.11.2026.
**Контекст:** требование «главное безопасность»; вход по email + паролю.
**Варианты:** Auth.js, Supabase Auth, своя реализация в Node, своя в Go.
**Решение:** своя в Go API: Argon2id, серверные сессии в Postgres, HttpOnly-cookie, TOTP для owner/superadmin.
**Правило паролей:** пароль никогда не сравнивается через `==` / plaintext. Только проверка против Argon2id-хэша (constant-time). Хэш не логируется и не отдаётся клиенту.
**Следствия:** полный контроль над блокировками, отзывом сессий и аудитом; криптография и auth — в одном Go-пакете.

## D-004. Роли и superadmin

**Дата:** 16.11.2026.
**Контекст:** разработчик должен иметь права чуть больше владельца клуба.
**Варианты:** один admin; owner + superadmin; отдельный системный аккаунт.
**Решение:** иерархия player → organizer → owner → superadmin. Superadmin создаётся только CLI, обязательная 2FA, не удаляет аудит, его действия видит владелец.
**Следствия:** матрица прав и защита от локаута обязательны; владелец не может управлять superadmin.

## D-013. Временный доступ и площадка на Raspberry Pi

**Дата:** 18.11.2026.
**Контекст:** на Pi 5 уже работают nginx на 80/443 и несколько чужих сервисов. Caddy из архитектурного плана занял бы те же порты. Нужен быстрый закрытый доступ к прототипу, пока нет базы данных, авторизации и 2FA.
**Решение:** приложение работает в Docker (Next.js standalone) на `127.0.0.1:3010`; внешний nginx проксирует его только по секретному префиксу `NEXT_BASE_PATH` и требует Basic Auth с длинным паролем. Корень домена и все прочие пути отдают 404. Сертификат Let's Encrypt выпускается certbot по webroot и продлевается существующим таймером. Сам домен — `mrpushkin.duckdns.org`.
**Следствия:** временную защиту нельзя считать заменой ролевой модели; при переходе на боевую авторизацию Basic Auth и секретный префикс убираются, nginx остаётся как TLS-терминатор. Смена поддомена DuckDNS требует токена аккаунта.
**Связано:** `docs/DEPLOY.md`, `deploy/`.

**Связано:** `docs/PRODUCT.md`, `docs/RATING.md`, `AGENTS.md`.

## D-015. Регистрация с подтверждением администратором

**Дата:** 18.11.2026.
**Контекст:** открытая регистрация нужна для роста лиги, но фейковые аккаунты и неверный уровень портят сетки и рейтинг.
**Решение:** любой может создать аккаунт; он получает статус `pending` и не может войти. Организатор проверяет и при необходимости исправляет имя, фамилию и уровень, затем подтверждает или отклоняет. Только после `approved` вход считается завершённым.
**Следствия:** появляется раздел `/organizer/applications`; решение фиксируется в аудите; до подтверждения вход заблокирован. В прототипе поток работает через localStorage, в продакшене — через БД и серверные actions.
**Связано:** `src/lib/accounts.ts`, `src/components/domain/AuthForms.tsx`, `src/app/organizer/applications/`.

## D-017. Backend на Go, UI на Next.js

**Дата:** 18.11.2026.
**Контекст:** нужен собственный сервер (не BaaS и не бизнес-логика внутри Next.js). Варианты языка сервера: Go или C++. Приоритет — безопасное соединение и корректная криптография паролей.
**Варианты:** (a) Next.js server actions + Drizzle; (b) отдельный API на Go; (c) отдельный API на C++.
**Решение:** UI — Next.js 16. API и вся авторизация/домен — Go. C++ отклонён: избыточен для CRUD/auth и дорог в сопровождении. Решение D-001 в части «логика в Next.js» заменено.
**Стек API:** Go 1.23+, `net/http` + chi, `pgx`, sqlc, goose, `golang.org/x/crypto` (argon2, и пр.).
**Безопасность в первую очередь:**
1. TLS на границе (nginx + Let's Encrypt); Go слушает только `127.0.0.1`.
2. Пароли — только Argon2id; проверка хэша, не plaintext.
3. Секреты приложения (TOTP и подобные) — AES-256-GCM, ключ `APP_ENCRYPTION_KEY` из env.
4. Сессии — случайный токен в cookie, в БД только SHA-256 хэш токена.
5. Бэкапы — шифрование `age` перед offsite.
**Следствия:** в compose появляются сервисы `api` и `db`; nginx проксирует `/api/` на Go; Next.js не ходит в Postgres напрямую; два рантайма (Node + Go) на Pi; документы и roadmap переписаны.
**Связано:** `ARCHITECTURE.md`, `ROADMAP` / план MVP.
