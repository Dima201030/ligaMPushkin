# Правила работы с продакшн-кодом

**Для кого:** AI-агенты и люди, которые меняют код лиги Mr. Pushkin.
**Статус:** обязательные правила. Если правило конфликтует с просьбой в чате, сначала
уточните, потом меняйте код.

---

## 1. Главный принцип

Код принадлежит продукту, а не агенту. Задача агента — внести минимальное понятное
изменение, проверить его и оставить репозиторий в состоянии, с которым сможет работать
следующий человек или агент.

Не переписывайте проект «чтобы стало красиво». Не превращайте задачу в рефакторинг.
Не трогайте файлы, которых задача не касается.

---

## 2. Тон и общение

### 2.1 Запрещено

- Комментировать правки пользователя и эмоционально реагировать на них:
  `!!! о я тут сделал вот как вы и просили!))`, `как вы и просили`, `я поправил ваш код`,
  `надеюсь, вам понравится`.
- Хвалить пользователя, задачу или себя: `отличная идея`, `прекрасный вопрос`,
  `я молодец`, `готово!`.
- Эмодзи, смайлики, восклицательные знаки в коде, документации, коммитах и интерфейсе.
- Вставлять в код «летопись» изменений: `// добавлено по просьбе`, `// new`, `// AI fix`.
- Отвечать на вопрос, который не задавали, и пересказывать свои действия в нескольких
  абзацах.

### 2.2 Как надо

- Нейтрально и по делу: что изменено, где, почему, как проверено.
- Если работа не завершена — сказать прямо, что осталось и что мешает.
- Если проверка не запускалась — не утверждать, что всё работает.
- Если пользователь изменил файл — прочитать актуальную версию и сохранить его правку.

Пример нормального ответа:

```text
Изменил поток регистрации: аккаунт создаётся со статусом «на проверке»,
организатор подтверждает имя, фамилию и уровень в /organizer/applications.
Проверка: npm run typecheck, npm run build, сценарий в браузере на 1440 и 390 px.
Ограничение: данные пока в localStorage, серверной авторизации нет.
```

## 3. Дисциплина изменений

1. **Сначала прочитайте файл.** Не редактируйте по памяти и не угадывайте содержимое.
2. **Минимальный диф.** Одна задача — одно логическое изменение. Не переформатируйте
   весь файл, не меняйте кавычки, отступы и порядок импортов «заодно».
3. **Не перезаписывайте чужие правки.** Если файл отличается от ожидаемого — разберитесь
   и сохраните намерение автора.
4. **Не удаляйте код, который кажется неиспользуемым,** без проверки ссылок и без
   подтверждения. Сначала поиск по репозиторию.
5. **Не переименовывайте публичные сущности** (маршруты, поля типов, классы дизайн-системы)
   без необходимости: это ломает ссылки и стили.
6. **Не добавляйте файлы «на будущее».** Новый модуль должен быть нужен сейчас.
7. **Не оставляйте мёртвый код, отладку и закомментированные блоки.**
8. **Не создавайте второй источник правды.** Данные — через `src/lib/data`, типы — в
   `src/lib/types.ts`, константы — в `src/lib/domain.ts`.

## 4. Код

- TypeScript без `any`. Если тип неизвестен — `unknown` и проверка.
- Компоненты по умолчанию серверные. `"use client"` — только когда нужны состояние,
  эффекты или браузерные API.
- Внутренние ссылки — `next/link`, не `<a href>`, иначе ломается `basePath`.
- Никаких `console.log` в продакшн-коде. Ошибки — через обработку и сообщение
  пользователю, позже — через Sentry.
- Никаких секретов, токенов и паролей в клиентском коде: всё, что попало в бандл,
  считается публичным.
- Валидация на сервере, не только в UI. UI — подсказка, не защита.
- Не добавляйте зависимость, если задача решается стандартными средствами. Если
  зависимость нужна — объясните, что она даёт и чем не подходит текущий стек.
- Соблюдайте стиль соседнего кода: имена, порядок пропсов, классы, форматирование.

### Комментарии

Комментарий объясняет **почему**, а не **что**. Очевидное не комментируется.

Плохо:

```ts
// устанавливаем статус
setStatus("pending");
```

Хорошо:

```ts
// Организатор подтверждает уровень вручную: автоматическая категория
// ошибается на игроках, которые вернулись после перерыва.
setStatus("pending");
```

## 5. Документация

- Меняете команды, структуру, поток или правило — обновите `README.md` и `AGENTS.md`.
- Меняете архитектурное решение — запись в `docs/DECISIONS.md` с датой, контекстом,
  альтернативами и следствиями.
- Меняете UI-систему — `docs/DESIGN.md`.
- Меняете рейтинг — `docs/RATING.md`.
- Меняете деплой — `docs/DEPLOY.md` и `deploy/`.
- Документация на русском. Технические имена и команды — как есть.

---

## 6. Секреты и безопасность

- `.env.deploy`, `.env`, `.env.local` не коммитятся и не печатаются в ответах.
- Пароли, Basic Auth, секретный путь и SSH-доступы не попадают в документацию в открытом
  виде. В docs — только имена переменных и место хранения.
- Не логируйте персональные данные: email, телефон, дату рождения, IP.
- Не отключайте проверки безопасности «для теста» в коде, который попадёт в main.
- Не ослабляйте CSP, rate limit и проверки ролей без отдельного решения.
- При сомнении считайте данные чувствительными.

## 7. Проверка

Перед завершением задачи:

```bash
npm run typecheck
npm run build     # если менялись маршруты, конфиг, серверный код или сборка
```

Для UI:

- 1440 px и 390 px;
- нет горизонтального скролла;
- ссылки работают с `basePath` (нет «голых» `/rating`, `/players` и т. п.);
- консоль без ошибок, изображения загружаются;
- клавиатурная навигация и подписи полей не сломаны.

Для регистрации:

- регистрация создаёт аккаунт «на проверке»;
- вход до подтверждения заблокирован с понятным сообщением;
- организатор подтверждает и может исправить имя, фамилию, уровень;
- после подтверждения вход ведёт в кабинет;
- отклонение показывает статус.

Не пишите «готово», пока не увидели результат проверки. В ответе укажите, что именно
запускали.

## 8. Git

- Ветка `main`, remote `origin` → `https://github.com/Dima201030/ligaMPushkin.git`.
- Коммит — атомарный, сообщение с префиксом:

```text
feat: подтверждение аккаунтов организатором
fix: ссылка на рейтинг внутри basePath
docs: правила для AI-агентов
```

- Не коммитьте `node_modules`, `.next`, `*.tsbuildinfo`, `.env.deploy`, `.DS_Store`.
- Не переписывайте историю и не делайте force-push без явного разрешения.
- Не пушьте, если задача не включает публикацию.

---

## 9. Деплой

- Деплой — только по задаче и только после зелёных `typecheck` и `build`.
- Скрипт: `./deploy/deploy-pi.sh`, секреты — в `.env.deploy`.
- Не печатайте пароли и секретный путь в логах и ответах.
- После деплоя проверьте: главная, турниры, рейтинг, вход, регистрация, кабинет
  организатора, заявки, картинки, HTTPS.
- Если что-то сломалось — сначала откат на предыдущий образ, потом разбор.

## 10. Данные и деструктивные действия

Без явного подтверждения запрещено:

- удалять или перезаписывать пользовательские данные, файлы и ветки;
- выполнять `git reset --hard`, `git clean -fd`, force-push;
- удалять миграции, таблицы, изображения и документы;
- менять настройки nginx, сертификаты и DNS;
- останавливать чужие сервисы на Pi.

Если действие потенциально необратимо — опишите риск и спросите.

## 11. Предметные ограничения

- Только взрослый теннис. Никаких детей, юниоров, детских турниров, лагерей и зачётов.
- Русский интерфейс, спокойный тон, без эмодзи и маркетингового шума.
- Один клуб, без мультитенантности.
- Онлайн-оплаты нет.
- Дизайн — EDITORIAL: бумага, чернила, Prata + Manrope, волосяные линии, только Lucide.
- Фотографии — временные, с сайта клуба.
